# #502 — Composite PK: INSERT column list, binding, and return-value semantics

Date: 2026-07-22
Issue: [#502](https://github.com/spiritEcosse/storm/issues/502) (parent #90, step 3 of 5)
Depends on: #500 (annotation + DDL), reuses the seam left by #501 (UPDATE/DELETE)

## The root fact

A single-column integer PK is generated by the database, so Storm omits it from the
INSERT and recovers it with `RETURNING id`. A composite PK has **no auto-generation
mechanism at all** — `AUTOINCREMENT` (SQLite) and `GENERATED ... AS IDENTITY` (PG) are
single-integer-column features; there is no auto-generated column *pair*. The caller
must therefore supply every part, which inverts today's rule: **PK columns must be
INSERTed**, because they are caller data.

## Decision: return type is B — `std::expected<void, Error>`, no `RETURNING`

Recorded on the issue before implementation, per its Definition of done.

Composite-PK `insert().execute()` returns `std::expected<void, Error>` and emits no
`RETURNING` clause, routing down the faster `ReturnId::No` path that already exists
(`queryset.cppm:87`). Single-PK models are untouched: `int64_t` + `RETURNING id`.
An explicit `insert<ReturnId::Yes>(...)` on a composite model is a compile-time error —
see the `ReturnId` table below.

Rejected alternatives:

- **A — `std::expected<std::tuple<...>, Error>`.** `RETURNING order_id, product_id` is
  valid on both backends, so this is not a technical limitation. It is rejected because
  the tuple hands back values the caller passed one line earlier, while making the return
  type vary by model shape — that ripples into generic callers and the `ReturnId::No`
  variant, and makes the DB produce a result row the insert path must step and extract.
- **C — keep `int64_t`, return the first PK column.** Silently lossy.

### `ReturnId` on a composite model

`ReturnId` is live public API, not an internal detail: `ReturnId::Yes` is the **default**
for single insert (`insert.cppm:362`) and is explicitly used in ~14 places in
`tests/crud/test_insert_returning.cpp`; `ReturnId::No` has its own test file
(`tests/crud/test_insert_no_return.cpp`). Both are reachable for single and bulk inserts,
so "composite returns void" is not a complete rule on its own — the explicit forms need
defining too.

| Call on a **composite** model | Result |
|---|---|
| `insert(obj)` (plain) | `expected<void, Error>`, no `RETURNING` |
| `insert<ReturnId::No>(obj)` | Same — accepted unchanged |
| `insert<ReturnId::Yes>(obj)` | **Compile-time error** |

`ReturnId::Yes` means "give me the DB-generated key", which for a composite PK does not
exist. Left unconstrained it would compile and emit `RETURNING <first_part>` — since
`build_insert_sql_array_impl<true>` appends `Base::pk_name_`, the first part only. That is
exactly rejected option C (silently lossy), reached through a back door. A `requires`
constraint rejects it at the call site instead, per CLAUDE.md rule 11 (`requires`, not
`throw`) and mirroring how #500 rejected `primary_autoincrement` + `primary_part` as
unrepresentable.

The rejection is deliberately **asymmetric**: only the affirmative request for a key is
refused. `ReturnId::No` remains valid on every model shape, so generic code that opts out
of the id keeps compiling across all models.

### The caveat was checked and does not fire

The issue flagged one thing that could force A: if a PK part could carry a DB-side
`DEFAULT` (#413), the caller would not know the stored value. Verified it cannot.
#413's `DEFAULT` is recovered at compile time from a **C++ default-member-initializer**
on a constexpr-constructible model (`schema.cppm:319`, `append_default_clause` reads
`constexpr Owner def{}`). That literal is a compile-time constant already present in the
caller's object — not a DB-generated value like a sequence. A PK part with a `DEFAULT`
still binds the caller's own value on every INSERT, so `RETURNING` would only echo the
input back. The issue's premise holds without exception.

## Change surface

Verified against the tree rather than taken from the issue text.

### 1. Column list and placeholders — `field_names.cppm`

`FieldNameGrammar::for_each_field_name<SkipPrimaryKey>` (line 27) skips on
`Base::all_members_[i] == Base::primary_key_` — the **first** PK part only. For a
composite model that would emit a column list missing part 1 while still binding it:
the exact shape of bug #501 fixed in the SET-target gate.

The skip test becomes `Base::is_pk_member(...)` gated on composite-ness, so:

- single-PK model → skips exactly its one PK (**byte-identical output**),
- composite model → skips nothing; every part joins the column list, placeholder list,
  and bind loop in declaration order.

This one function feeds `calculate_field_names_size_impl`, `build_field_names_list_impl`,
and `build_placeholders`, so the sizer, the list, and the placeholder count cannot drift
apart — the consteval sizer stays exact by construction.

### 2. Bind — `base.cppm`

INSERT binds through `bind_non_pk_fields_impl` / `bind_non_pk_objects_bulk_impl`, which
pass `SkipPrimaryKey=true` into `bind_field_at_index`. #501 already landed the needed
seam: `skips_pk_column<SkipPK, SkipAllPK>` (line 904), whose comment explicitly reserves
the INSERT widening for this issue. Composite INSERT therefore skips nothing by routing
through that existing flag — no third flag is introduced.

### 3. `placeholders_count()` — `insert.cppm:530`

Returns `Base::field_count_ - 1`, hardcoding "exactly one skipped PK". **Not listed in
the issue.** It feeds the upsert DO UPDATE path's `auto_update` `now()` bind offset, so a
composite model would bind the timestamp tail one slot early. Becomes
`field_count_ - (has_composite_pk_ ? 0 : 1)`.

### 4. Bulk prefix and its cache — `insert.cppm:212-229`

`build_bulk_insert_prefix` calls the same `build_non_pk_field_names_list()`, so it
follows from change 1 with no independent edit. Its separate size constant
(`calculate_bulk_insert_prefix_size`) calls the same sizer, so it stays consistent.

### 5. Chunking — no change needed

Auto batch size is `MAX_DB_VARIABLES / Base::field_count_` (`insert.cppm:445,469`) —
divided by **all** fields. Today that over-counts for single-PK models (which bind
`field_count_ - 1` per row); for composite models it becomes exactly right, since every
field is now bound. The 999-parameter ceiling therefore holds automatically. Asserted at
the boundary rather than modified.

### 6. Return type plumbing — `insert.cppm` / `queryset.cppm`

Composite models select the non-`RETURNING` SQL and the `void` result. The
`build_insert_sql_array_impl<WithReturning>` template already has both arms; composite
models force `WithReturning=false`, and the `RETURNING`-suffix constants
(`returning_suffix_array`, line 232, which appends `Base::pk_name_`) are simply not
instantiated for them.

### 7. The `ReturnId::Yes` constraint

A named concept gates the affirmative request, constraining the `ReturnId`-templated
`query()` overloads (`insert.cppm:362,381`) and the matching `QuerySet::insert`
overloads (`queryset.cppm:89,103`) so the error fires at the **call site** rather than
deep inside SQL construction. Constraining both layers matters: `QuerySet::insert` is the
public entry point, and an unconstrained wrapper would report the failure from inside
`query()` instead.

Gating on the concept — not on `has_composite_pk_` inline — follows the #472/#477/#478
precedent of naming compile-time preconditions, and keeps the diagnostic readable.
`ReturnId::No` is left unconstrained on purpose.

## Testing

Written **before** implementation and confirmed failing first (CLAUDE.md rule 9).
Model fixtures already exist from #501 in `tests/crud/test_composite_pk_models.h` and are
reused unchanged: `OrderLine` (2 int parts), `Inventory` (int + string), `Ledger`
(3 parts, mixed widths), `StockEntry` (FK part — canonical association table), `Widget`
(single-PK control).

| Case | Asserts |
|---|---|
| Single insert, composite | Row lands with both parts as supplied; `execute()` is `expected<void>` |
| SQL text | Column list, placeholder count, and declaration order; **no** `RETURNING` |
| Batch insert | All rows land; every part correct per row |
| Batch at chunk boundary | `999 / field_count` rows, and one past it, all land |
| Duplicate composite key | Surfaced as `Error`, not a crash or silent success |
| Mixed-type parts | `Inventory`, `Ledger` — bind dispatches per part type |
| FK part | `StockEntry` — column named `warehouse_id`, binds the referenced key |
| `ReturnId::No`, composite | Accepted; `expected<void>`, no `RETURNING`; row lands |
| `ReturnId::Yes`, composite | **Rejected at compile time** — asserted on the gate predicate, not via a real call (see below) |
| Single-PK regression | INSERT SQL **byte-identical**; `RETURNING id` path unchanged; `ReturnId::Yes`/`No` both still work |

The negative-compile case is asserted as `static_assert(!ReturnIdSupported<OrderLine, Yes>)`
on the gate predicate itself, plus the positive controls
(`ReturnIdSupported<Widget, Yes>`, `ReturnIdSupported<OrderLine, No>`). A test cannot
contain the ill-formed call it is asserting about, so the assertion targets the concept —
the established pattern in this tree for negative-compile coverage.

Cross-backend via `TYPED_TEST` over `DatabaseTypes` (SQLite + PostgreSQL).
